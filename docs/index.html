RustySqueezer

A fake LLM for context compaction: deterministic, extractive thread summaries with no language model involved.

GitHub repository Build status Full README

Why it exists

Agents compact long threads by sending the whole thread to a summarising model. That request must fit inside the summariser's context window, so a local model with a modest window (e.g. 131k tokens) cannot compact its own threads, and you end up paying a 1M-context cloud model for every compaction event.

The insight: compaction does not need a model. It needs a good extractive summary of what was asked, what was run, what broke, and what was just said. RustySqueezer does exactly that, in a few milliseconds, for free, and always produces byte-identical output for the same input (which keeps prefix caches warm).

agent -- POST /v1/chat/completions -- structured summary (5-10% of thread)

How it works

The chat-completions endpoint parses the messages array and builds a markdown summary from the thread:

  1. Detect the compaction request: if the last user message matches known compaction instruction patterns (Zed, Claude Code-style compact, generic "summarize the conversation so far"), it is treated as an instruction and removed from the thread.
  2. Split the thread into the original task, follow-up user messages, shell commands actually run, file paths touched, error lines, and the most recent verbatim tail of turns.
  3. Score assistant sentences with a TF-IDF-ish term-importance heuristic and keep the highest-scoring key points.
  4. Apply per-section budgets: every section gets its own slice of MAX_SUMMARY_CHARS; the verbatim tail gets the largest share, and surplus items are dropped with an explicit omission note, so long threads never lose their tail.
  5. Optional: add highlights from a small local model when ASSIST_ENABLED is true. If the assist call fails, the section is skipped and the output stays deterministic.

Sections and default budgets

SectionDefault shareWhat it contains
tail50 %most recent turns, verbatim (newest first, clipped)
commands12 %shell commands actually run, most recent first
followups10 %later user messages
key_points10 %highest-scoring assistant sentences
errors8 %error/failure lines
files8 %file paths mentioned by tools
original_task6 %first user message
tools4 %distinct tool names
assist2 %optional small-model highlights

Quick start

cd rust
cargo run   # or: docker compose up -d
curl -s localhost:8000/health
curl -s localhost:8000/v1/models

API

MethodPathBehaviour
GET/healthhealth check with model id
GET/v1/modelssingle model id (MODEL_NAME)
POST/v1/chat/completionsOpenAI-compatible; returns the summary of the thread it was given (streaming or non-streaming)
curl -s localhost:8000/v1/chat/completions -H 'content-type: application/json' -d '{"model":"rustysqueezer","messages":[{"role":"user","content":"Fix the nginx upstream timeout in docker/traefik"},{"role":"assistant","content":"I ran docker compose up -d; failed exit code 1."},{"role":"user","content":"Please summarize conversation so far"}]}'

The usage field reports token counts from the deterministic tokenizer, so completion_tokens / prompt_tokens is the real compression ratio.

Configuration

Two layers, both optional:

  • Environment variables (see .env.example) - simple knobs.
  • A JSON config file (CONFIG_PATH, see config.example.json) - detection rules, error/file patterns, enabled sections, titles and budgets. Unknown keys are ignored, partial maps merge, and MAX_* / TAIL_* env variables still win over the file.
VariableDefaultMeaning
PORT8000listen port
MODEL_NAMErustysqueezermodel id on /v1/models

ASSIST_ENABLEDfalseadd highlights from a small local model via ASSIST_MODEL_URL

Evaluation

eval/eval.py (stdlib only, no dependencies) replays synthetic threads with known needles - facts that must survive compaction - against a live instance and reports needle recall, compression ratio, determinism and budget compliance:

python3 eval/eval.py --url http://localhost:8000/v1

Scenarios include a ~190k-token tool-heavy thread. The harness fails (non-zero exit) if recall drops below the threshold or a section exceeds its budget, so it doubles as a regression gate before deploying an update, and it runs in CI.

Deployment

CI (the build-image workflow) builds on every push to main and publishes to GitHub Container Registry; deployments never build from source:

TagContents
ghcr.io/handtrixx/rustysqueezer:latestRust binary from rust/Dockerfile
ghcr.io/handtrixx/rustysqueezer:shasame, pinned to a commit
docker run -d -p 8000:8000 -e MAX_SUMMARY_CHARS=12000 ghcr.io/handtrixx/rustysqueezer:latest

The binary is about 3.5 MB and starts instantly; rust/compose.yml is a ready-made single-service compose file.

Wiring into an agent

Zed

Declare the endpoint as an OpenAI-compatible model with a large context window in ~/.config/zed/settings.json under language_models.openai_compatible, then point agent.compaction_model at it.

LiteLLM

Add an openai/rustysqueezer entry in litellm_config.yaml pointing at http://localhost:8000/v1 with a large max_tokens.

Anything else

Any harness that picks a summariser via an OpenAI-compatible chat endpoint can use RustySqueezer as a drop-in.

Limitations

  • Extractive, not abstractive: nuance is lost in very long, meandering threads.
  • Heuristics (error regex, sentence splitting, file patterns) are tuned for code-agent traffic; retune them via config.json for other harnesses.
  • Token counting is word-boundary based, not exact cl100k BPE.
  • Only the OpenAI chat-completion surface is implemented - no Anthropic messages API, no embeddings, no tool calling.
  • No authentication: run it on a private network or behind a reverse proxy.
