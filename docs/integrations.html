    • Quick start

    docker run -d -p 8000:8000 ghcr.io/handtrixx/rustysqueezer:latest
curl -s localhost:8000/health

    Endpoints: OpenAI POST /v1/chat/completions, Anthropic POST /v1/messages (including native compaction blocks), Ollama POST /api/chat and POST /api/generate, plus GET /health and model discovery. No auth, no model, no network: bodies up to 64 MiB (a roughly 1M-token thread) compact in well under a second.

    Integration overview

    Two ways to use RustySqueezer: client-side - the agent has a compaction-model setting and you point it at RustySqueezer; or gateway-side - LiteLLM's auto-router compacts the thread before dispatch, which works for clients with no compaction setting at all (VS Code).

    Zed

    Zed lets you name an explicit compaction model for the agent. Declare RustySqueezer as an OpenAI-compatible provider with a large declared context window, then point both compaction settings at it.

    {
              "language_servers": [],
              "agent": {
                "compaction_model": "rustysqueezer",
                "thread_summary_model": "rustysqueezer"
              }
            }

    The provider itself goes in the models section of settings.json:

    {
              "openai_compatible": {
                "rustysqueezer": {
                  "base_url": "http://localhost:8000/v1",
                  "api_key": "none",
                  "max_tokens": 1000000
                }
              }
            }

    Why a big max_tokens: compaction fires when the thread approaches the window Zed believes the model has. Declaring 1M tokens lets whole long sessions reach RustySqueezer in one request (it accepts bodies up to 64 MiB), which is exactly what you want from a summarizer.

    LiteLLM gateway

    LiteLLM plays two roles here. You can call RustySqueezer as a plain model through the gateway, or let the gateway itself compact the thread before dispatching to a real model - useful for clients that have no compaction setting of their own.

    1. RustySqueezer as a model

    model:
  - model: "openai/rustysqueezer"
    api_base: "http://rustysqueezer:8000/v1"
    max_input_tokens: 1000000
    max_output_tokens: 4096

    Point any LiteLLM client at rustysqueezer to use it as the summarizer directly (the analogue of Zed's agent.compaction_model).

    2. Gateway-side automatic compaction

    LiteLLM's auto-router supports native context management: when an incoming thread approaches the declared window, it summarizes the old turns with a chosen compactor model before forwarding the trimmed request to the target model.

    model:
  - model: "anthropic/claude-sonnet-5"
    max_input_tokens: 200000

router:
  auto_router:
    complexity_router:
      context_compaction:
        model: "rusty-compactor"
        trigger_ratio: 0.9
        max_tokens: 4096
        timeout_seconds: 120

model:
  - model: "rusty-compactor"
    alias: "rusty-compactor"
    api_base: "http://rustysqueezer:8000/v1"
    max_input_tokens: 1000000

    The compaction trigger is floor(max_input_tokens x trigger_ratio) - max_output_tokens. With a 200k window and ratio 0.9, threads above roughly 176k tokens get compacted before the real model sees them.

    Gotcha (verified 2026-10-30): if the summary plus the retained tail still exceed the router's budget, LiteLLM raises a 400 ContextWindowExceededError. Keep max_tokens in the compaction block comfortably below the target window, and use RustySqueezer 1.0.6 or newer, which handles very large inbound threads (up to 64 MiB) reliably.

    VS Code (GitHub Copilot)

    Copilot has no user-settable compaction model - the agent decides compaction internally. So the gateway route is the way: run LiteLLM in front of RustySqueezer and point Copilot at LiteLLM as a custom OpenAI-compatible provider.

    1. Configure LiteLLM as in the LiteLLM section: a router alias with an honest (or deliberately large) declared window, and context_compaction on the auto-router with rusty-compactor as the compactor.
    2. In VS Code set github.copilot.chat.customOAICompatibleEndpoint (or the Copilot "models" provider settings) to your LiteLLM base URL.
    3. Copilot sends full threads to LiteLLM; LiteLLM compacts anything over the trigger and forwards a trimmed thread to the real model.

    Why it works: compaction becomes invisible to the client. Any tool that speaks OpenAI chat completions through a gateway - VS Code, OpenCode without native compaction, internal scripts - benefits without a per-client setting.

    OpenCode

    OpenCode supports a native compaction model (the same idea as Zed's agent.compaction_model), so you can point it at RustySqueezer directly, or route through LiteLLM for gateway-side compaction.

    Native compaction model

    {
  "agents": {
    "general": {
      "compaction": {
        "model": "litellm/rustysqueezer"
      }
    }
  }
}

    With the provider declared via the OpenAI-compatible SDK:

    {
  "provider": {
    "litellm": {
      "npm": "@ai-sdk/openai-compatible",
      "baseURL": "http://localhost:4000/v1",
      "models": {
        "rustysqueezer": {
          "name": "RustySqueezer",
          "limit": { "context": 1000000, "output": 4096 }
        }
      }
    }
  }
}

    Note: OpenCode's compactor sends its own summarization instructions with the thread. RustySqueezer is extractive and deterministic, so it works, but adding OpenCode's instruction wording to the instruction_patterns list (via CONFIG_PATH) gives cleaner summaries. Its "type": "native" Responses-API context management is OpenAI-specific and does not apply here.

    Tuning the heuristics

    RustySqueezer's extraction rules are tunable without recompiling: mount a JSON config via CONFIG_PATH (see config.example.json in the repo) or override the individual knobs with environment variables.

    Env varDefault-ish meaning
    MODEL_NAMEReported model id for discovery endpoints
    MAX_SUMMARY_CHARSCap on the generated summary
    TAIL_TURNS / TAIL_CHARSHow many recent turns (or chars) are kept verbatim
    MAX_COMMANDSShell commands kept from the thread
    MAX_FILESFile paths / edits kept
    MAX_ERRORSFailed commands and tracebacks kept
    MAX_KEY_POINTSOther salient statements kept

    Measure the effect on real threads with the eval harness:

    python3 eval/real_thread.py --url http://localhost:8000/v1 --transcript thread.json

    FAQ

    Is the output deterministic?

    Yes. Same thread in, same summary out - no sampling, no model weights, no network calls. Good for reproducible evals.

    How big a thread can it handle?

    Request bodies up to 64 MiB. A roughly 1M-token Zed session compacts in about 0.1 s at around 4 MB RSS.

    Are the token counts exact?

    No - counting is word-boundary based, not cl100k BPE. It is close enough for trigger thresholds but do not treat it as ground truth.

    Should I keep a real fallback model?

    Recommended. RustySqueezer is extractive; for long, meandering threads where nuance matters, point the compaction setting at a real small model and use RustySqueezer for the bulk of sessions.
